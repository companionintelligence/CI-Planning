## 5. Playwright segmentation plan

The container suite is already split into named Playwright projects in `tests/container/playwright.config.ts`; the plan is to keep each project selectable by the app/auth fixture it needs and grow cross-layer coverage where the current unit and browser layers do not meet.

| Project / phase | Flow | Scope and fixture | Gate plan |
|---|---|---|---|
| `smoke`, `auth-local`, `auth-portal` (implemented) | Delivery headers, app boot, service worker and sign-in | Existing container; fixture portal and local test identity | Run smoke and both auth contracts on pull requests. |
| `tasks` (implemented; extend) | Open → details → note → complete; swipe task actions | Owner-scoped task fixtures; cleanup only seeded rows | Keep task journey on pull requests. Add browser checks for right-swipe staging, left-swipe Archive/Delete, persisted state after reload, and restore; component tests already cover gesture handling. |
| `planner`, `objectives` (implemented) | Stage → schedule → inspect → undo; objective create → complete → progress | Owner-scoped task, block and objective fixtures with deterministic calendar data | Run the feature projects on pull requests that touch these flows; keep placement and overlap assertions deterministic. |
| `agent`, `metrics` (implemented) | Ask → clarify → review → confirm; write → metrics → recap; suggestion → feedback | Stubbed planner/model responses, owner-scoped records and rolling-window deltas | Run on pull requests with no live model dependency; preserve the no-write-before-confirm assertion. |
| `integrations` (implemented contract slice) | Provider unavailable, Google and push contracts | Mocked provider error and fixture identities; live Google/push accounts are excluded | Run mocked contracts on pull requests; keep live-provider checks opt-in or in an isolated scheduled environment. |
| `responsive`, `mobile`, `accessibility` (implemented for audited surfaces) | Short viewport, close/focus return, axe, keyboard, reduced motion and larger text | Named phone/tablet/desktop viewports and light/dark themes | Run the affected responsive/a11y project when a surface changes; run the full matrix nightly. |
| `data-flow` (proposed) | Browser write → database → SSE event → second read/derived metric | One owner-scoped seeded record; assert the event and reloaded API/UI state | Add after the task swipe journey; run selected high-value flows on pull requests and the full matrix nightly. |

Execution rules: use role/name locators, seed only test-owned data, and attach trace/screenshots on failure. Keep fast unit rules in Vitest. Split the planned `data-flow` project by user-visible journeys rather than by backend route, so each case proves the browser action, owner-scoped write, event/read refresh and derived result together.

| Priority | Finding | Recommendation |
|---|---|---|
| High | Several large view and feature modules still mix composition, stateful workflows and interactive surfaces. The TaskCard objective and routine workflows have been extracted; six production files remain above 800 lines. | Continue extracting cohesive route-owned sections and hooks, keeping views as composition, stores/API as state and transport boundaries, and `lib/` as reusable domain logic. ### Suggested web compartmentalization refactor

1. **Hold the current boundaries:** route views compose screens; feature components own their local interaction; `stores/` owns shared reactive state and refresh rules; `lib/` owns transport helpers and pure domain logic; `ui/` owns presentation primitives and recipes. Keep business rules out of `ui/`.
2. **Create feature homes incrementally:** group new and extracted code under `client/src/features/{tasks,planner,objectives,focus,agent,metrics,settings,auth}/`, each with components, feature hooks and colocated tests. Keep existing routes stable and re-export where a gradual move needs a compatibility seam.
3. **Start with high-coupling surfaces:** split `Settings`, `ElementWizard`, `DetailsDrawer`, `Planner` and `TaskCard` into named subpanels and hooks; avoid one-file-per-component churn for small, cohesive views.
4. **Make overlay choices explicit:** use `ModalSheet` for dialogs and sheets; use `ViewportOverlay` for non-modal backdrops or positioned surfaces. Keep keyboard focus, Escape, focus restoration, safe-area and z-index behavior in the shared boundary.
5. **Centralize static visual rules:** tokens for semantic color/radius/elevation; feature recipes for repeated action rows, form grids, cards and headers; CSS custom properties for runtime geometry and user-selected color. Preserve intentional brand and chart palettes as named exceptions.
6. **Ship in vertical slices:** Tasks → Planner/Flight Plan → Objectives → Focus/Agent → Metrics/Settings. For each slice, move behavior without changing route/store/API contracts, add the matching Vitest component tests, and extend the matching named Playwright project for the browser-visible flow and responsive state.
