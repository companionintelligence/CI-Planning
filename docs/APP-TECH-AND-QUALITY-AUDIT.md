**Reviewed:** 2026-11-23

**Scope:** source-level architecture and test inventory, the Today/Planner cockpit screenshot, a cross-component style review, and follow-up browser accessibility verification. ## 6. Front-end style audit and compartmentalization

### Inventory and observed style system

| Item | Finding |
|---|---|
| Surface size | 144 TSX files in `client/src/components/`, 18 TSX files in `client/src/views/`; 168 TSX files total across the client. |
| Shared visual foundation | `client/src/index.css` imports Tailwind and the CI token package, defines light/dark semantic CSS variables, global controls (`.btn-*`, `.input`, `.view-*`), navigation and drawer styles. Tailwind config maps legacy color names to semantic variables. |
| Component styling | Most layout and spacing are utility classes; feature views also include dynamic inline CSS for data-driven colors, widths and timeline placement. The original source scan found 122 `style=` occurrences; after the presentation cleanup it finds 106. Dynamic schedule geometry and data-selected colors remain inline. |
| Screenshot evidence | The current narrow Today/Planner cockpit keeps navigation and day controls visible. With the Details/Flight Plan drawer open, the drawer consumes most of the vertical viewport and leaves only a small slice of Planner visible; this is a high-value mobile-flow target for responsive testing. |

### Findings

| Priority | Finding | Recommendation |
|---|---|---|
| High | The app has shared semantic tokens and global primitives, but feature modules still compose many low-level utilities and hand-built action rows. Similar modal, card, header, toolbar and empty-state patterns can drift across the 144 shared components. | Define a small set of accessible, responsive primitives (PageHeader, Toolbar, Card, Modal/Sheet, FormField, EmptyState, ActionMenu, DataList) and migrate by feature slice. Avoid a wholesale rewrite. |
| High | Planner, Details drawer, Flight Plan and floating assistant compete for limited mobile canvas. The captured 430 × 900 state shows the drawer dominating the work area. | Keep the single-surface model and viewport regression in place; extend mobile bounds and focus-return checks to the other modal and drawer families. |
| Medium | Inline styles still exist across features, but fixed visual treatments are now isolated in semantic classes and token-backed recipes; runtime geometry/color remains inline where it comes from schedule, task, or user data. | Continue the cleanup by feature slice when those components are next touched; avoid moving data-derived values into hard-coded classes. |
| Medium | Utility class strings encode component-specific spacing, typography, and states directly in JSX, so related controls can drift during iterative mobile fixes. | Adopt feature-level style recipes for recurring elements, e.g. Planner card actions and modal field grids. Document component contracts and responsive variants beside the shared primitive. |
| Medium | Accessibility can vary by view and state; representative screens now have browser checks, but Settings, dialogs and additional touch targets remain unaudited. | Keep the axe, keyboard, reduced-motion, text-scaling and 44px target checks in CI; extend coverage to Settings, dialogs and additional mobile controls as those feature slices are updated. |

**Implementation status (2026-11-23):** `client/src/ui/` now provides shared PageHeader, Toolbar, Card, Modal/Sheet, FormField, EmptyState, ActionMenu and DataList primitives. Balance Metrics is the first migrated slice, using the shared header, control group, cards and empty states. Existing components in other features are intentionally left for later vertical-slice migrations; the primitives are a foundation, not a claim that all 144 components have already been migrated.

**Tasks slice status (2026-11-23):** The Tasks view now composes the shared PageHeader, Toolbar, Card and EmptyState primitives for page actions, list controls, filter panel, collapsible sections and empty results. Task data and interactions remain in the Tasks feature; this slice only standardizes its surface structure and accessibility semantics. TypeScript validation passes.

**Planner / Flight Plan slice status (2026-11-23):** Flight Plan now uses the shared Card, Toolbar and EmptyState primitives for its named region, action group and empty/search states. A feature recipe keeps its header controls wrapped within the mobile sheet. Scheduling, selection and persistence remain in the existing component and API contracts.

**Task detail / notes slice status (2026-11-23):** The task drawer's notes section now uses the shared Card and Toolbar primitives, with a feature recipe for timestamped note entries that wraps long content within the drawer. The browser task flow checks the Notes heading and action group before adding and verifying a persisted note; note storage and editing remain in the existing API flow.

**Objectives slice status (2026-11-23):** ObjectiveModal now uses the shared ModalSheet and FormField primitives, with a fixed footer slot so Save/Cancel stays reachable while tall forms scroll. The container flow confirms child creation preselects its parent, choosing None creates a root objective, and the mobile quick-add creates a linked task with initialized progress.

**Mobile compartment status (2026-11-23):** Details and Flight Plan use one visual-viewport-bounded mobile sheet with a dimmed, non-interactive canvas, a preserving Back action, an explicit close-and-clear action, and a direct assistant switch. CSS bounds the sheet against dynamic viewport height even if JavaScript viewport measurements lag, and closing returns focus to the opener or drawer toggle. The authenticated Playwright flow checks bounds at 430 × 900 and 430 × 560, the named Flight Plan region and action group, assistant switching, and keyboard focus. It passed in the local container smoke run and is wired into CI. Other modal/drawer families and physical keyboard-device coverage remain future work.

**Responsive sheet status (2026-11-23):** The task editor now has dialog semantics, a keyboard focus trap, focus restoration and a named close control. The responsive Playwright project checks task editor and Objective sheet bounds at 430 × 560 and 430 × 420, and verifies close returns focus to the opener. The check waits for the sheet entrance animation to settle before evaluating final geometry. It passed in the local container gate and is wired into CI. Remaining modal/drawer families and tablet/desktop viewport checks remain future work.

**Inline style status (2026-11-23):** Repeated/static treatments for brand labels, approval outlines, onboarding backdrops, safe-area padding, icon strokes, star/day fills, chart markers, card outlines, animation delays, and wizard drag feedback now use shared CSS recipes backed by semantic tokens. Planner coordinates, progress widths, user-selected colors, and other data-driven values remain inline. The scan dropped from 122 to 106 occurrences; this is a targeted cleanup, not a claim that all feature styling has been centralized.

**Feature recipe status (2026-11-23):** `client/src/ui/recipes.css` documents the contracts and narrow-screen behavior for Planner action menus and modal form layouts. The Planner quick-action menu and Objective modal use those recipes: actions share alignment and hit-area rules, objective field pairs stack on mobile and form two columns at 40rem, and footer actions can share the available width on very narrow screens. Extend recipes by feature slice when adjacent controls are updated; keep content-specific visual states semantic on the control.

**Accessibility regression status (2026-11-23):** `tests/container/accessibility.spec.ts` injects axe-core and checks Today/Planner, the open Flight Plan sheet, Tasks and the Appearance/accessibility settings card in light and dark themes, including WCAG color contrast. It also checks keyboard-visible focus, browser reduced-motion behavior, larger-text scaling, and minimum 44px targets for mobile navigation, More, and the task-assistant FAB. All three accessibility checks and the mobile compartment check passed in the local container smoke run. The scans wait for route entrance animation to finish so contrast is measured at stable opacity. The initial scan found light-theme contrast and Tasks tab semantics issues; the implementation now uses a higher-contrast muted token, puts filters outside the tablist, and labels the direction select. A follow-up scan also raised the compact Flight Plan action text to the primary token after finding a 4.31:1 contrast ratio. Other Settings sections and dialogs remain outside the axe gate. `axe-core` is test-only and does not ship in the app runtime.

**Playwright segmentation status (2026-11-23):** `tests/container/playwright.config.ts` now defines named `smoke`, `auth-local`, `auth-portal`, `tasks`, `planner`, `objectives`, `agent`, `metrics`, `responsive`, `mobile` and `accessibility` projects. `tests/container/run-local.sh` and the container publish workflow select the project matching each app/auth fixture explicitly, avoiding unrelated and intentionally skipped specs in those phases. Package scripts expose the same project selectors for focused runs. Task, Planner, Objective, Agent and Metrics projects use owner-scoped fixture setup/cleanup where persisted data is involved. Implemented journeys cover task detail → note → completion, Flight Plan stage → auto-schedule around a meeting → verify adjacent non-overlapping placements → undo, Time Block title edit → persist, overlapping task block → edit time → clear warning, Objective parent prefill → clear to top-level → add a task directly from the mobile objective → complete the task → verify progress and edited status, assistant ask → clarify with conversation history → edit draft title/duration → verify no write before confirmation → confirm and verify persisted tasks, task completion/rating/time → Daily Completion and Metrics totals → compare the assistant's read-only 7-day recap, and task/Objective sheets → short viewport bounds → close → focus return. Planner drag/resize, suggestion-learning outcome fixtures, and agent bulk/partial-failure journeys remain uncovered.

### Suggested web compartmentalization refactor

1. Keep domain boundaries in `views/` and `components/`; do not split solely by file size.
2. Add `client/src/ui/` for stable primitives and style recipes, without task/scheduling business logic.
3. Group feature composition under `client/src/features/{tasks,planner,objectives,focus,agent,metrics}/`, moving view-specific components with their view while preserving shared domain services in `lib/` and `stores/`.
4. Treat overlays as viewport-level compartments with one stacking contract, focus management, safe-area and keyboard handling.
5. Refactor in vertical slices: Planner/Flight Plan, task edit/detail, objectives, then Focus/metrics and Settings. Keep route behavior and store/API contracts unchanged in each slice.
6. After each slice, compare desktop/mobile screenshots and run the new Playwright project for that slice; use Vitest for isolated component logic.

### Audit limits

The visual review covers the captured Today/Planner shell state, not every route, modal, theme, or device. The source audit inventories all TSX files but is not a rendered review of every individual component. Axe currently covers Today/Planner, Tasks and the Appearance/accessibility card in both themes; other Settings sections, dialogs, other touch targets and the broader mobile/tablet/desktop screenshot matrix remain outside the current automated checks. Passing browser checks do not establish a measured unit-test coverage percentage.
